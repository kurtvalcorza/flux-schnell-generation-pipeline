# Weight provenance, the mirror-staged snapshot and DIMER hosting

This repository pins **two** Hugging Face snapshots, each with its own `dimer-base-manifest.json` (format `dimer_hf_snapshot` v1: byte size and SHA-256 per file, the immutable revision, the licence) and each staged and verified separately by `src/flux_schnell_generation_pipeline/pipeline.py`. Every weight file is safetensors; nothing is unpickled, and the model classes come from `diffusers`, `transformers`, `peft` and `bitsandbytes` on PyPI — no Hub-hosted code is executed.

## 1. The model — FLUX.1 [schnell], identity of record and staging source

- Upstream (identity of record): `black-forest-labs/FLUX.1-schnell`, immutable revision `741f7c3ce8b383c54771c7003378a50191e9efe9` (the repository's `main`; created 2024-07-31, last modified 2024-08-16 according to the Hub API). The repository is **gated** (`gated: auto`, a click-through): its files download only after accepting the gate, and its file listing shows LFS digests as `****` to anyone who has not. Its commit history is also hidden behind the gate.
- Upstream weight license: **Apache-2.0** (`license: apache-2.0` in the upstream front matter, `LICENSE.md` in the upstream tree, and the upstream README's own statement that the model "can be used for personal, scientific, and commercial purposes").
- Staging source: `unsloth/FLUX.1-schnell`, revision `9df3faa7ae3b6ddf0b2b69bb78616372897cc65c` (created 2026-08-05), whose README states it is an ungated, unmodified mirror of the upstream repository. `stage_missing_files()` fetches missing manifest entries from this repository at this revision and nowhere else (a test asserts the downloader's target); `verify_snapshot()` checks that the manifest names this source and then checks every byte against the committed digests, so the host that served a file cannot change what is loaded.
- **Byte-identity evidence, as of 2026-09-20:**
  - The 23 pinned paths exist in the upstream tree under the same names with the **same byte sizes** (checked through the ungated tree API: `/api/models/black-forest-labs/FLUX.1-schnell/tree/741f7c3c…`). The upstream tree has 28 files; the mirror has the same 28 plus a `NOTICE`; the only size difference is `README.md` (3,681 upstream vs 3,994 mirror — the mirror's banner). Upstream LFS SHA-256 digests are masked behind the gate and have **not** been compared yet; accepting the gate once (the maintainer's action) would expose them and close the proof.
  - The mirror's transformer shard 1 (9,962,580,296 bytes, SHA-256 `9b633dbe…`) and the single-file `flux1-schnell.safetensors` (23,782,506,688 bytes, `9403429e…`) carry the same digests across ten independent ungated re-uploads inspected on 2026-09-20 (unsloth, lzyvegetable, frankjoshua, YuCollection, tripathiarpan20, chutesai, exolabs, nick911, AITRADER, JSCreatorPro) — one digest from many uploaders, which is consensus, not proof.
  - Until the gate is accepted the honest statement is: *the snapshot loaded here is exactly the committed manifest, which matches the upstream file for file and byte for byte in size, and matches every other public copy in digest.*
- **Mirror caveats, and why the manifest is narrower than the mirror:** the mirror's `NOTICE` file carries the FLUX.1 [dev] Non-Commercial licence text — a copy error, since the mirror's own front matter, the upstream front matter and the upstream `LICENSE.md` all say Apache-2.0 — and the mirror has no `LICENSE` file although its README points to one. The manifest therefore pins **only the 23 diffusers-layout files** the pipeline loads and excludes the mirror's `README.md` and `NOTICE`, the single-file BFL checkpoints `flux1-schnell.safetensors` (23.8 GB) and `ae.safetensors` (0.34 GB), and `schnell_grid.jpeg`. Nothing the mirror added or relabelled is inside the verified perimeter.
- Local layout: `weights/flux1-schnell/` holds the 23 manifest entries (33,725,923,002 bytes): `model_index.json`; `scheduler/scheduler_config.json` (`FlowMatchEulerDiscreteScheduler`, `shift 1.0`, `use_dynamic_shifting false`, 1,000 training timesteps); `text_encoder/{config.json, model.safetensors (246,144,352 bytes, `893d67a2…`)}` (CLIP-L, 123 M parameters, bfloat16); `text_encoder_2/{config.json, model.safetensors.index.json, model-00001-of-00002.safetensors (4,994,582,224 bytes, `ec87bffd…`), model-00002-of-00002.safetensors (4,530,066,360 bytes, `a5640855…`)}` (T5-XXL encoder, 24 layers, d_model 4,096, 4.76 B parameters, bfloat16); `tokenizer/{merges.txt, special_tokens_map.json, tokenizer_config.json, vocab.json}` (CLIP BPE); `tokenizer_2/{special_tokens_map.json, spiece.model, tokenizer.json, tokenizer_config.json}` (T5 SentencePiece + fast tokenizer); `transformer/{config.json, diffusion_pytorch_model.safetensors.index.json, diffusion_pytorch_model-00001-of-00003.safetensors (9,962,580,296 bytes, `9b633dbe…`), …-00002-of-00003 (9,949,328,904 bytes, `58b44340…`), …-00003-of-00003 (3,870,584,832 bytes, `e2cbc254…`)}`; `vae/{config.json, diffusion_pytorch_model.safetensors (167,666,902 bytes, `f5b59a26…`)}`. The small JSON/tokenizer files are committed; the seven safetensors and `spiece.model` (an LFS object) are git-ignored or fetched and verified at run time.
- Architecture (`transformer/config.json`): `FluxTransformer2DModel` — 19 double-stream (`transformer_blocks`) and 38 single-stream (`single_transformer_blocks`) blocks, 24 heads × 128 = hidden size 3,072, `in_channels 64` (16 latent channels packed 2 × 2), `joint_attention_dim 4096` (T5), `pooled_projection_dim 768` (CLIP-L), `guidance_embeds false` (guidance-distilled: no classifier-free guidance). The three shards hold 1,156 tensors and 11,891,178,560 parameters in bfloat16 (read from the safetensors headers on 2026-09-20).

- Upstream: `laion/CLIP-ViT-B-32-laion2B-s34B-b79K`, revision `1a25a446712ba5ee05982a381eed697ef9b435cf` (2025-01-22), MIT licence.

## Fidelity

No upstream regression fixture is published for the transformer, and the 4-bit load changes the function being run. The evidence is the load of all 1,156 tensors into `FluxTransformer2DModel` from the pinned `config.json` through bitsandbytes NF4, the parameter count asserted by `build_transformer` (packed 4-bit tensors counted at their original shape), the LoRA tensor count asserted at injection (380), and generation that CLIP recognises: the frozen 4-bit model's 512² four-step renderings of the six bird captions are classified among the six captions by CLIP with the accuracy recorded in `MODEL_CARD.md` (*Runtime*) and `release-verification.md`. What quantisation costs against the bfloat16 checkpoint is **not** measured here — the bfloat16 transformer does not fit the reference runtime.

## Runtime facts

- Precision: transformer weights NF4 (bitsandbytes 4-bit NormalFloat with double quantisation; the linear projections of all 57 blocks) with float16 compute on CUDA by default (`COMPUTE_DTYPE`; `bfloat16` is accepted for GPUs with native support — a T4 has none), LoRA parameters float32 with autocast and loss scaling, VAE float32 (`force_upcast`), text encoders float16 on CUDA. CPU is refused: 4-bit needs CUDA and the transformer would need 48 GB of RAM in float32.
- Residency: the text encoders (9.7 GB in float16) and the 4-bit transformer (about 6.6 GB) do not fit a 16 GB GPU together with anything else. `encode_prompts` refuses to load the encoders while the transformer is resident; `load_transformer` releases the encoders first; the reload step of the tutorial releases the adapted transformer before the fresh one loads.
- Generation: 4 Euler steps (`DEFAULT_STEPS`, `MAX_STEPS = 8`) with `guidance_scale 0.0` (the model has no guidance embedding), one seeded CPU generator per image (image *i* uses `seed + i`), prompt embeddings from the cache (`text_encoder=None`, `text_encoder_2=None` in the upstream `FluxPipeline`), latents returned packed and decoded through the float32 VAE by the pipeline itself.
- Evaluation: the held-out flow-matching MSE re-encodes each photograph with the VAE (seeded posterior sample, shifted and scaled), packs it, mixes it with seeded noise at σ = 0.1 / 0.3 / 0.5 / 0.7 / 0.9 (x_σ = (1 − σ)·x₀ + σ·ε) and scores the transformer's velocity prediction against ε − x₀; the same seed gives identical inputs for the frozen and the adapted model.
- Adaptation: LoRA rank 8 / alpha 8 on `to_q`, `to_k`, `to_v` of all 57 blocks and `to_out.0` of the 19 double-stream blocks (the single-stream blocks fuse their output projection into `proj_out`, which is not targeted) — 190 modules, 380 tensors, 9,338,880 parameters (0.08 % of the transformer) — injected with `peft.inject_adapter_in_model` over the 4-bit base (QLoRA); AdamW, grad-norm clip 1.0, uniform σ, batch size 1, gradient checkpointing, epoch selected by validation loss with the frozen model as epoch 0 (LoRA B = 0 at initialisation, so epoch 0 *is* the frozen model); transactional on failure; the LoRA tensors are written in place so the quantised base is never re-serialised.
- `diffusers`, `transformers`, `peft`, `bitsandbytes`, `accelerate`, `sentencepiece` (for the T5 tokenizer) and `protobuf` are the runtime pins beyond torch; the package imports all of them lazily so manifest verification and input validation run first (fleet RTM-001). On hosted images whose system CUDA is older than the one torch was built against, `build_transformer` preloads the pip-bundled NVIDIA libraries before importing `bitsandbytes` (fleet trap F8).

## The tutorial data: pinned iNaturalist CC0 photographs

`samples.py` fetches 60 research-grade iNaturalist photographs of six North American birds (Song Sparrow, Chipping Sparrow, White-throated Sparrow, Dark-eyed Junco, House Finch, American Goldfinch — 10 per species, one per observer per species) from the public open-data bucket `https://inaturalist-open-data.s3.amazonaws.com/photos/<photo id>/medium.<ext>`, 5,789,324 bytes in all, each pinned by byte size and SHA-256 in `SAMPLE_RECORDS` and refused on a mismatch before decoding; every photo is CC0 1.0 and its observation page and observer are recorded. Captions come from one template per species. `build_sample_dataset` draws a seeded 6 / 2 / 2 stratified split per species (36 / 12 / 12); the cache is `weights/inat-birds/` (git-ignored).

## DIMER hosting

- **Status: HOLD (upload)** by the maintainer's decision of 2026-09-20. The E2E carrier is built and verified independently of that decision.
- **Provenance gate:** the identity of record is gated; the bytes come from a mirror. Before any hosting, the maintainer accepts the upstream gate once and compares the upstream LFS digests with the manifest (this file is then updated from "same sizes, consensus digests" to "identical digests"). A profile must name the upstream identity and licence, not the mirror.
- **Size:** the served set is the 23 diffusers-layout files, 33.7 GB (transformer 23.8 GB bfloat16, T5-XXL 9.5 GB, CLIP-L 0.25 GB, VAE 0.17 GB) — far above the fleet's 9 GB publication convenience gate. A pre-quantised NF4 export of the transformer (about 6.6 GB) would be a maintainer-converted file with a new digest, which this repository does not produce; the pipeline quantises at load time from the published bfloat16 shards.
- **Upload set (if hosted):** the `transformer/`, `text_encoder/`, `text_encoder_2/`, `tokenizer/`, `tokenizer_2/`, `vae/` and `scheduler/` folders plus `model_index.json`; the scorer is evaluation-only and not part of a serving profile. No pickle exists anywhere in the set.
- Loader trust boundary: no `trust_remote_code`, no Hub-hosted code, safetensors only; the classes are `diffusers.FluxTransformer2DModel` (through `diffusers.BitsAndBytesConfig`), `diffusers.AutoencoderKL`, `diffusers.FlowMatchEulerDiscreteScheduler`, `transformers.CLIPTextModel`, `transformers.T5EncoderModel`, `transformers.AutoTokenizer` and `diffusers.FluxPipeline` at the pinned versions.
- Serving shape: generation needs the 4-bit transformer (about 6.6 GB) and the VAE (0.34 GB in float32) resident, plus either both text encoders (9.7 GB in float16, which do not fit beside the transformer on 16 GB) or pre-encoded prompt embeddings; a 512² image at 4 steps takes the seconds recorded in `release-verification.md` on a T4. An adapted profile adds a 380-tensor LoRA adapter of about 37 MB (float32), valid over the NF4 base only.
- Line endings: `.gitattributes` carries `weights/** -text`, so a Windows checkout cannot rewrite a snapshot file's newlines and break its recorded digest.
